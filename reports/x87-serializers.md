# Canonical x87 state-image evidence

Updated 2026-09-06 13:16 UTC. Image helper checks pass within explicit profiles. No startup instruction selector or game compilation coverage was added; P3 remains open.

`native/semantics/x87_environment.h` packs and imports the 28-byte legacy environment, reconstructs full tags, rotates raw payloads when TOP changes, normalizes control words and packs legacy/64-bit FXSAVE images. The helper keeps the final 96 software-owned bytes untouched and uses canonical x87 payloads and XMM values rather than the stale serialized register cache. Pointer segments and save policy are explicit parameters.

The native data-helper fixture performs 5,242,880 checks: 196,608 stack/profile inputs, 2,097,152 arbitrary full-tag imports, 65,536 control-word imports and 196,608 AMD pointer-policy witnesses. Intel hardware supplies layout and state observations; AMD witnesses check the documented conditional byte writes, not AMD execution. All compared fields pass with one separately counted host pointer-loss observation. The audit verifies raw summaries, binaries, source snapshots, retained failures and the unchanged accepted v9 module.

The first two runs each failed on one FXSAVE64 observation at different inputs. Additional logging isolated offsets 12/13 and 20/21: the upper halves of both saved pointers became zero. A separate hardware-only probe loads known full pointers, delays with integer instructions/PAUSE, then saves them. All 1,025 changed cases among 263,168 inputs show exactly this truncation; the delayed groups account for 1,006 of 1,024 cases. Affinity pinning does not prevent it. This measures a host preservation problem and does not identify the exact kernel cause. Windows documents an XMM_SAVE_AREA32 member in its 64-bit CONTEXT, and the supplied SDK declares 32-bit ErrorOffset/DataOffset fields; that is consistent with the observation but is not proof of a specific save path. [Microsoft CONTEXT reference](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-context).

The passing serializer run accepts this host observation only if both pointers are truncated exactly to 32 bits and every other saved byte matches. It independently verifies that the native serializer preserves the full canonical values. It records one truncation and 196,607 exact full-pointer hardware matches. It does not silently drop pointer comparisons or claim that all hardware bytes agree.

Primary AMD text states that FXSAVE may omit last instruction/data/opcode pointers unless the exception-summary bit is set. It also describes nonwaiting saves and legacy versus offset64 pointer layouts. This is why the image profile is explicit. The text is available through the primary-source search index; direct API retrieval currently returns 404. [AMD volume 5, FXSAVE](https://docs.amd.com/api/khub/documents/w13cmcpL4f9MCT4WPN6eDg/content), [AMD volume 1, section 6.9.1.2](https://docs.amd.com/api/khub/documents/sfvvekC9mDflu6vd3R0NXA/content).

The layout probe also checks every 16-bit control input for FLDCW and FLDENV: all normalize to `(input & 0x1f3f) | 0x40` on the Intel host. The 28-byte opcode field is at byte 18, unlike the pinned Remill FSAVE struct's opcode member at byte 10. These helpers use explicit field offsets and do not alias that struct.
